This one bites almost everyone who moves from QtWebKit to QtWebEngine, and it is two separate
problems wearing the same costume — a page that just doesn't load, with no exception and no
log line.

**1. Initialisation order.** `QNetworkProxy::setApplicationProxy()` has to be called *before*
the `QApplication` is constructed. Chromium's network process reads the application proxy
during startup; set it afterwards and your call is simply ignored. No error is raised, which
is what makes it so hard to spot.

```python
# BEFORE QApplication - this ordering is load-bearing
proxy = QNetworkProxy()
proxy.setType(QNetworkProxy.ProxyType.HttpProxy)
proxy.setHostName("proxy.example.com")
proxy.setPort(8080)
proxy.setUser("username")
proxy.setPassword("password")
QNetworkProxy.setApplicationProxy(proxy)

app = QApplication(sys.argv)
```

**2. The 407 is not answered for render-process requests.** This is the part that matches your
symptom exactly — the tunnel is established, but `Proxy-Authorization` never goes out. Chromium
does not reuse the `QNetworkProxy` credentials for requests issued by the render process. You
have to answer the challenge explicitly:

```python
def on_proxy_auth(url, authenticator):
    authenticator.setUser("username")
    authenticator.setPassword("password")

view.page().proxyAuthenticationRequired.connect(on_proxy_auth)
```

Connect it on the *page*, and connect it before the first `load()`. If the signal is never
connected, the request is cancelled silently — Qt gives you no error callback here at all.

**Then verify, rather than trusting the page.** A page that renders is not evidence the proxy
was used; if the config silently failed you are simply browsing direct. Load an echo endpoint
and compare:

```python
view.load(QUrl("https://api.ipify.org"))
```

If that shows your own IP, the proxy is not in the path regardless of how healthy everything
looks. Worth checking DNS too — Qt WebEngine resolves hostnames locally by default, so names
can leak even when traffic is proxied correctly (see qutebrowser issue 5731 for the detail).

A couple of things that catch people after the above:
- `applicationProxy` is process-global, so per-view proxies aren't possible this way. The usual
  workaround is a separate process per proxy with `--proxy-server=`.
- On Linux the system proxy is not always picked up from the desktop environment, even though
  the docs suggest it should be.
